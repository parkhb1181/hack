# SPEC — 파서 · 스키마 · 지표 규격

`PRD.md` v1.2 부속 문서. **공식과 파라미터는 이 문서에서만 바꾼다.**

---

## 1. 도메인 개념

용어를 먼저 고정한다. 여기가 흔들리면 구현 중 반복적으로 되돌아온다.

| 용어 | 정의 |
| --- | --- |
| **버스트** | 같은 화자의 연속 메시지 묶음. 정의상 화자가 교대하므로 두 사람의 버스트 수는 항상 ±1 |
| **세션** | 직전 메시지와 **6시간 이상** 벌어지면 새 세션. 시간 판정의 **유일한** 임계값 |
| **전환 쌍** | `(상대 버스트의 마지막 메시지, 내 첫 응답)`. 응답 지연·동조율의 계산 단위 |
| **판독 창** | 가장 최근 메시지 120개. **헤드라인 계산 범위** |
| **정보 단위** | 표본 크기 척도. 타입 가중 합 (§6.1) |

캡처 입력에서 이미지 간 연결이 끊긴 지점은 **세션 경계로 간주하지 않고 불확정 경계로 표시**한다. 캡처 3~4장은 통상 단일 세션이다.

## 2. 공통 메시지 포맷

두 파서가 이 구조 하나로 수렴한다. **D1 종료 시점까지 이 포맷 확정이 전체 성공 조건이다.**

```ts
type Msg = {
  seq: number                 // 병합·정렬 후 최종 순서
  who: 'me' | 'other'
  ts: number | null           // epoch ms. 캡처는 대부분 null
  date: string | null         // 'YYYY-MM-DD'. 캡처는 구분선 보일 때만
  time: string | null         // 'HH:mm' (24h 정규화 완료)
  type: 'text' | 'photo' | 'emoticon' | 'file' | 'voice' | 'deleted'
  text: string | null         // type === 'text' 일 때만 채움
  charCount: number           // type !== 'text' 이면 무조건 0 (강제)
  emojiDesc: string | null    // Vision 2패스. 캡처 전용
  affect: { valence: number; intensity: number } | null   // 캡처 전용
  confidence: number          // txt = 1.0, 캡처 = Vision 반환값
}

type Corpus = {
  mode: 'txt' | 'capture'
  source: 'kakao_pc' | 'kakao_android' | 'unknown'
  messages: Msg[]             // 전체
  window: Msg[]               // 최근 120개 (헤드라인용)
  availableFields: Set<Field>
  infoUnits: number
  windowFilled: number        // window.length
  gaps: string[]              // 'ts_missing' | 'scroll_break:img2' | 'name_merged:2->1'
}

type Field = 'who' | 'ts' | 'date' | 'time' | 'text' | 'type' | 'affect' | 'continuity'
```

`seq`, `who`, `type`은 필수. 나머지는 null 가능이며 **null 여부가 지표 가용성을 결정한다.**

`charCount = 0` 강제는 미디어가 분량 지표를 오염시키는 것을 막는 유일한 방어선이다. `사진`(2자), `이모티콘`(4자)을 그대로 세면 미디어를 많이 보내는 쪽이 분량에서 유리해진다.

## 3. txt 파서

### 3.1 핵심 발견 — CRLF가 레코드 구분자

**실파일 검증 완료** (PC 23,465 메시지 / 안드 16,976 메시지):

| | PC | 안드로이드 |
| --- | --- | --- |
| CRLF | 28,051 | 19,432 |
| 순수 LF (메시지 내부 줄바꿈) | 2,828 | 2,337 |
| 멀티라인 메시지 | 1,222 | 1,019 |
| CRLF 분할 후 미분류 레코드 | **0** | 0 (시스템 메시지 제외) |

```js
const records = text.split('\r\n')   // 레코드 1개 = 메시지 1개
```

**멀티라인 문제가 이 한 줄로 해결된다.** 정규식 이어붙이기 로직은 안전망으로만 유지한다(직전 메시지가 있고 어떤 패턴에도 안 맞으면 `\n` + 이어붙임).

### 3.2 전처리

```js
let s = new TextDecoder('utf-8').decode(buf)
if (s.charCodeAt(0) === 0xFEFF) s = s.slice(1)   // 안드로이드 BOM
```

### 3.3 정규식 세트

```js
// --- PC (카카오톡 데스크톱) ---
const PC_TITLE = /^(.+?) 님과 카카오톡 대화$/;
const PC_DATE  = /^-{5,}\s*(\d{4})년 (\d{1,2})월 (\d{1,2})일 [월화수목금토일]요일\s*-{5,}$/;
const PC_MSG   = /^\[(.+?)\] \[(오전|오후) (\d{1,2}):(\d{2})\] ([\s\S]*)$/;

// --- 안드로이드 ---
const AN_TITLE = /^(.+?) 님과 카카오톡 대화$/;
const AN_MSG   = /^(\d{4})년 (\d{1,2})월 (\d{1,2})일 (오전|오후) (\d{1,2}):(\d{2}), (.+?) : ([\s\S]*)$/;
const AN_SYS   = /^(\d{4})년 (\d{1,2})월 (\d{1,2})일 (오전|오후) (\d{1,2}):(\d{2}), (.+)$/;
const AN_DATE  = /^(\d{4})년 (\d{1,2})월 (\d{1,2})일 (오전|오후) (\d{1,2}):(\d{2})$/;  // 맨 타임스탬프 1줄

// --- iOS 감지용 (지원 안 함) ---
const IOS_HINT = /^\d{4}\. \d{1,2}\. \d{1,2}\. (오전|오후) \d{1,2}:\d{2}/;

// --- 공통 시스템 (타임스탬프 없음) ---
const SYS_NOTS = /^(.+님이 (들어왔|나갔)습니다\.|메시지가 삭제되었습니다\.|관리자가 메시지를 가렸습니다\.|방장이 [\s\S]*변경되었습니다\.[\s\S]*)$/;
```

### 3.4 검사 순서 — 반드시 지킬 것

```
1. DATE / 구분선
2. MSG          ← 먼저
3. SYS          ← 나중
4. 미매칭 → 직전 메시지에 이어붙임 (안전망)
```

**2↔3을 뒤집으면 `시어머니님` 같은 닉네임의 메시지가 시스템 메시지로 오분류된다.** 실제 파일에 존재하는 닉네임이다.

### 3.5 포맷 감지

앞 200 레코드에서 `PC_MSG` / `AN_MSG` / `IOS_HINT` 매칭 수를 세고 최다를 채택. `IOS_HINT`가 최다면 거부 + 안내.

### 3.6 시각 정규화 — 필수

```js
let h = parseInt(hh)
if (ampm === '오전' && h === 12) h = 0
if (ampm === '오후' && h !== 12) h += 12
```

**실측: PC 562건 / 안드 425건의 `오전 12시` 메시지 존재.** 변환하지 않으면 자정 대화 1,000건이 정오로 튀고 세션 분할이 통째로 깨진다.

### 3.7 날짜 상태

- **PC**: `PC_DATE` 구분선으로 현재 날짜를 들고 간다. 구분선을 놓치면 그 뒤 전체 날짜가 틀어진다
- **안드로이드**: 줄마다 완전한 날짜. 상태 불필요 (구조적으로 더 안전)

### 3.8 닉네임 엣지 케이스

| 케이스 | 실측 | 처리 |
| --- | --- | --- |
| `]` 포함 닉네임 (`adsp 최고[2일전사] 80점합격`) | 존재 | `(.+?)\]` non-greedy + 백트래킹으로 정상 처리됨. 검증 완료 |
| ` : ` 포함 닉네임 | 695명 중 0명 | 1차 파싱으로 고빈도 화자 집합 구축 → 2차에서 고정 문자열 교대(alternation)로 재매칭 |
| `님`으로 끝나는 닉네임 (`시어머니님`) | 존재 | §3.4 검사 순서로 방어 |

### 3.9 제외/별도 처리

| 유형 | 패턴 | 처리 |
| --- | --- | --- |
| 미디어 | `사진`, `사진 N장`, `동영상`, `이모티콘`, `음성메시지` | `type` 분류, `charCount = 0` |
| 파일/샵검색 | `파일: …`, `샵검색: #…` | 동일 |
| 삭제 | `메시지가 삭제되었습니다.` | 완전 제외 (타임스탬프 없음 → 시간축 배치 불가). 총량만 카운트 |
| 시스템 | 입퇴장·방장변경 | 제외 |

### 3.10 Web Worker 스펙

```js
const reader = file.stream().pipeThrough(new TextDecoderStream()).getReader()
let carry = ''
while (true) {
  const { value, done } = await reader.read()
  if (done) break
  const buf = carry + value
  const parts = buf.split('\r\n')
  carry = parts.pop()          // 마지막 미완결 조각 보관 ← 필수
  parts.forEach(handleRecord)
  postMessage({ progress: bytesRead / file.size })
}
if (carry) handleRecord(carry)
```

**캐리 버퍼 없으면 20MB에서 확률적으로 깨진다.** 청크가 `\r`과 `\n` 사이에서 잘릴 수 있다.

**반환 계약**: Worker는 `Msg[]` 전량을 메인 스레드로 넘기지 않는다. 반환물 = 집계 결과 + 판독 창 120개 + 명장면 후보 발췌(상한 100) + 화자 목록. 수십만 메시지 객체를 넘기면 모바일 OOM.

### 3.11 화자 판별과 병합

- 제목 줄 `{상대} 님과 카카오톡 대화`와 불일치하는 화자 = 나. 실패 시 드롭다운
- **3명 이상 감지 시 즉시 거절하지 않는다.** 화자별 메시지 비중 + 활동 기간을 표시하고, 소수 화자가 시간적으로 겹치지 않으면(A는 3월까지, B는 3월부터) **동일인 병합을 제안**한다. 닉네임 변경이 1:1을 단톡으로 오탐하는 것을 막는다
- 병합 후에도 3명 이상 → 거절
- 표시명은 확정 즉시 `A` / `B`로 치환. 원본 이름 미보관

## 4. 캡처 파서

### 4.1 파이프라인

```
이미지 N장 → Vision 1패스(병렬, 장당 1회) → 겹침 제거 병합
           → Vision 2패스(emoticon·photo 항목 배치 1회) → Corpus
```

프롬프트 전문은 `MODELS.md`.

### 4.2 겹침 중복 제거

사용자는 스크롤하며 겹치게 캡처한다. **지표 계산 전 단계에서 반드시 처리.** 안 하면 메시지수 비대칭이 통째로 왜곡된다.

```
normalize(m) = { side: m.side, text: m.text?.trim().replace(/\s+/g,' '), time: m.time }

merge(A, B):
  for k = 15 down to 2:                       // 큰 겹침부터 시도
    if equalSeq(A.slice(-k), B.slice(0, k)):
      return [...A, ...B.slice(k)]
  return [...A, ...B]  + gaps.push('scroll_break')   // 겹침 없음으로 간주
```

- 비교 단위: `(side, text, time)` 튜플 — 텍스트만 비교하면 `ㅇㅇ`·`ㅋㅋ`가 오매칭
- **최소 연속 매칭 길이 2** — 단건 일치로 병합하지 않음
- 윈도우 15 — 5는 실제 스크롤 겹침(6~10개)을 못 잡는다

**이것은 모델이 아니라 알고리즘이다.** 발표에서 "모델이 병합한다"고 말하지 않는다. 엔지니어링 역량은 병합으로, 모델 필요성은 C급 지표로 각각 증명한다.

### 4.3 순서 정렬

파일명 자연 정렬 → 사용자 드래그 수동 조정. **Vision에 순서 추론을 맡기지 않는다.**

### 4.4 자정 넘김 — 실제로 터지는 버그

캡처에는 날짜가 없고 시:분만 있다. `23:58 → 00:03`은 **−23시간 55분**으로 계산된다.

```js
let delta = t2 - t1                    // 분
if (delta < 0) delta += 1440           // 자정 넘김 가정
if (delta > 360) return EXCLUDE        // 6시간 초과 → 다른 날일 수 있음, 전환 쌍에서 제외
```

조각난 캡처에서는 실제로 며칠 차이일 수 있으므로, 보정 후에도 6시간을 넘으면 버린다.

### 4.5 잘린 말풍선

캡처 상하단의 첫 줄·마지막 줄은 `confidence`를 낮게 부여하고 병합 시 우선순위를 낮춘다. Vision 프롬프트에서 "내용을 확신할 수 없으면 제외"를 지시하되, 넘어온 경우 대비.

### 4.6 다크모드

**배경색 기반 좌우 판별 로직을 짜지 않는다.** 정렬 위치로만 판단하도록 Vision에 지시하고, 코드는 Vision의 `side`를 그대로 신뢰한다.

## 5. 지표 카탈로그

### 5.1 레지스트리

```ts
type MetricStatus = 'OK' | 'LOCKED' | 'INSUFFICIENT'

type MetricSpec = {
  key: string
  grade: 'A' | 'B' | 'C'
  requires: Field[]                    // 없으면 LOCKED
  minSamples: number
  sampleCounter: (c: Corpus) => number // 없으면 INSUFFICIENT
  scope: 'window' | 'full'             // 판독 창 vs 전체
  compute: (c: Corpus) => unknown
}

function evaluate(spec: MetricSpec, c: Corpus): MetricResult {
  const missing = spec.requires.filter(f => !c.availableFields.has(f))
  if (missing.length) return { status: 'LOCKED', missing }
  const have = spec.sampleCounter(c)
  if (have < spec.minSamples) return { status: 'INSUFFICIENT', have, need: spec.minSamples }
  return { status: 'OK', value: spec.compute(c) }
}
```

**`LOCKED`와 `INSUFFICIENT`를 구분한다.** 앞은 "다른 입력이 필요하다", 뒤는 "더 많이 필요하다"이며 사용자에게 할 말이 다르다.

### 5.2 카탈로그

| key | 지표 | 등급 | requires | 하한 | scope | txt | 캡처 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `msgCount` | 메시지수 비대칭 | A | who | 메시지 30 | window | ○ | ○ |
| `msgLength` | 평균 길이 비대칭 | A | who, text | 메시지 30 | window | ○ | ○ |
| `questionRate` | 질문 버스트 비율 | A | who, text | 버스트 20 | window | ○ | ○ |
| `syncAsym` | 동조율 방향 비대칭 | A | text, embedding | 전환 쌍 20 | window | ○ 옵트인 | ○ |
| `styleSep` | 말투 분리도 | A | text, embedding | 화자당 30 | window | ○ 옵트인 | ○ |
| `replyDist` | 응답 분포 | A | time, who | 전환 쌍 20 | full | ○ | △ 세션 내 한정 |

## 6. 표본 처리

### 6.1 정보 단위

메시지 개수 대신 쓰는 표본 크기 척도. `ㅇㅇ` 200개와 의미 있는 문장 20개의 정보량은 다르다.

| 타입 | 가중치 |
| --- | --- |
| 텍스트 10자 이상 | 1.0 |
| 텍스트 3~9자 | 0.7 |
| 텍스트 2자 이하 | 0.4 |
| 이모티콘 (`affect` 있음) | 1.2 |
| 이모티콘 (`affect` 없음, txt) | 0.1 |
| 사진 | 0.3 |

> **짧은 메시지 상향 (0.1 → 0.4 / 0.4 → 0.7, 2026-08-05).** 원래 값은 "짧은 말은
> 정보가 없다"는 가정에서 나왔는데, 한국어 카톡에서는 틀렸다. 실물 대화에서
> `안` `아남` `집이여` 같은 1~3자가 대화의 절반을 차지하고, 그것들이 바로
> **누가 먼저 말을 걸고 누가 답하는지**를 나른다 — A급 지표 대부분이 이 짧은
> 차례로 계산된다. 실측: 캡처 3장에서 지표 6개가 `OK`인데 정보 단위만 12.7이라
> §6.2 하한에 걸렸다. 막고 있던 것은 신뢰도가 아니라 가중치였다.
>
> `ㅇㅇ` 200개를 문장 200개와 같게 보지 않는다는 원래 취지는 유지된다 —
> 여전히 1.0이 아니라 0.4다.

> **주의**: 이모티콘 가중치는 `affect`가 있을 때만 높다. txt의 `이모티콘` 플레이스홀더는 정보량이 실제로 0에 가까우므로 0.1이다. 이 비대칭이 §PRD 3.1의 "손실 포맷" 주장을 숫자로 증명한다.

### 6.2 하드 플로어

**정보 단위 10 미만이면 리포트를 만들지 않는다.** 대신 단일 카드 하나:

> 이 대화에서 확실히 말할 수 있는 것 하나
> **답장은 상대가 두 배 느립니다**

지표 3개짜리 결과에 "분석 완료"를 붙이면 도구 전체의 신뢰가 무너진다.

> **40 → 25 → 10 (2026-08-05).** 40은 txt 경로를 기준으로 잡은 값이라 캡처 경로를
> 사실상 전부 거절했다. 실물 카톡 캡처 3장(말풍선 23 + 비텍스트 3 = 26건)에서
> 정보 단위가 **14**로 나왔고, 40에 닿으려면 캡처가 9~11장 필요했다. 3장 올리는
> 것이 정상 사용인데 그 경로가 항상 막혔다. 그 입력에서도 지표는 이미 6개가
> `OK`였으므로, 하한이 막고 있던 것은 신뢰도가 아니라 캡처 경로 자체였다.
>
> 25로도 부족했다 — §6.1 가중치를 올린 뒤에도 캡처 3장이 16.6이었다. **10은
> "캡처 두어 장이면 무엇이든 보여준다"는 선택이다.** 이 하한에서 하드 플로어는
> 사실상 빈 입력만 거른다.
>
> **거르는 일은 §6.4 정밀도 하향이 대신 맡는다.** 표본이 얇으면 리포트는 나오되
> 숫자를 숨기고 밴드 라벨만 보여준다 — "많이 기울어 있습니다"는 나가고
> "기울기 +51"은 안 나간다. 얇은 표본에 정밀한 숫자를 붙이지 않는다는 §6.2의
> 원래 취지는 그쪽에 남아 있다.

### 6.3 축소 추정 (비율 지표)

세션 3개 중 3개가 100%로 표시되는 것을 막는다.

```
p̂ = (x + m × 0.5) / (n + m),   m = 8
```

세션 3개 중 3개 → 원값 100% → **축소값 68%**. 표본이 늘면 원값에 수렴한다.

### 6.4 정밀도 하향

표본이 하한의 1.5배 미만이면 소수점을 버리고 3구간 라벨로 떨어뜨린다. 세션 5개로 뽑은 값에 `78.4%`를 쓰는 것은 없는 정밀도를 주장하는 것이다.

> 먼저 말 건 쪽: **대체로 나**

### 6.5 부트스트랩 신뢰구간 *(시간 남으면)*

임베딩 지표에 한해 복원 추출 200회. 벡터를 재계산하지 않고 중심 계산만 반복하므로 수십 ms.

> 말투 분리도 **41** (28~55)

구간이 과도하게 넓으면 값 대신 구간만 표시.

## 7. 헤드라인 — 기울기

### 7.1 축 설계

`총 글자수 = 메시지수 × 평균 길이`이고, 버스트 수는 구조상 양쪽 동일(±1)이므로 "버스트당 평균 메시지"는 메시지수 비대칭과 같은 축이다. **곱을 분해해 이중 계상을 구조적으로 제거한다.**

```
norm(a, b) = (a + b) === 0 ? 0 : (a - b) / (a + b)

I_메시지수 = norm(내 메시지수,        상대 메시지수)
I_길이     = norm(내 평균 charCount,  상대 평균 charCount)    // text 메시지만
I_질문     = norm(내 질문 버스트 비율, 상대 질문 버스트 비율)   // '?' 포함 버스트 / 전체 버스트
I_동조     = norm(동조_나,            동조_상대)              // 임베딩 가용 시에만
```

**모든 계산은 판독 창(최근 120개) 기준.**

### 7.2 결측 처리 — 0으로 채우지 않는다

```js
const axes = [I_메시지수, I_길이, I_질문]
if (embeddingAvailable) axes.push(I_동조)
const tilt = Math.round(100 * axes.reduce((a,b)=>a+b, 0) / axes.length)
```

**0은 "균형"을 의미한다.** 없는 축을 0으로 채우면 결측이 방향을 균형 쪽으로 왜곡한다. 가용 축만으로 평균 후 재정규화한다.

화면에 근거 개수를 표시한다:

> **기울기 +62** · 4개 축 중 3개로 산출

### 7.3 밴드

| 밴드 | 범위 | 라벨 |
| --- | --- | --- |
| `strong_me` | +55 ~ +100 | 이 대화는 당신 쪽으로 뚜렷하게 기울어 있습니다 |
| `lean_me` | +20 ~ +54 | 당신 쪽으로 기울어 있습니다 |
| `even` | −19 ~ +19 | 한쪽으로 기울었다고 보기 어렵습니다 |
| `lean_other` | −54 ~ −20 | 상대 쪽으로 기울어 있습니다 |
| `strong_other` | −100 ~ −55 | 이 대화는 상대 쪽으로 뚜렷하게 기울어 있습니다 |

라벨은 전부 **"이 대화"**를 주어로 쓴다. 사람에 대한 판정이 아니라 이 입력 안의 신호에 대한 관찰이라는 걸 라벨 자체가 말해야 한다.

`windowFilled < 60`이면 숫자를 숨기고 밴드 라벨만 표시한다(§6.4).

### 7.3.1 썸 모드 라벨 (`stage === 'crush'`)

같은 기울기라도 읽는 방향이 다르다. 다른 관계에서 `+`는 중립 관찰이지만 썸에서는 "나만 다가가고 있다"로 읽힌다. **문구만 바뀌고 계산은 동일하다** — 지표 코드는 `stage`를 보지 않는다(§4.2 원칙 유지).

| 밴드 | 썸 라벨 |
| --- | --- |
| `strong_me` | 당신이 훨씬 더 많이 다가가고 있습니다 |
| `lean_me` | 당신 쪽에서 더 다가가고 있습니다 |
| `even` | 양쪽이 비슷하게 주고받고 있습니다 |
| `lean_other` | 상대 쪽에서 더 다가오고 있습니다 |
| `strong_other` | 상대가 훨씬 더 많이 다가오고 있습니다 |

썸 라벨도 관찰형을 유지한다. "가망", "포기" 같은 판정 어휘 금지는 여기서도 동일하다(PRD §4.5).

### 7.3.2 신호 요약 점수

썸 모드 화면에만 표시하는 0~100 값. **기울기의 좌표 변환이며 새로운 계산이 아니다.**

```
신호 = round(50 - tilt / 2)      // tilt −100 → 100, 0 → 50, +100 → 0
```

높을수록 상대 쪽 신호가 강하다. **이 값은 예측이 아니다.** 화면에는 항상 다음 둘과 함께 표시한다.

1. 구성 축의 방향 (메시지 수 / 평균 길이 / 질문 / 맞춰주는 정도)
2. 고정 문구 — `예측이 아닙니다. 아래 지표를 합쳐 옮긴 값입니다.`

> 학습 데이터도 정답 라벨도 없으므로 "이어질 확률"은 계산할 수 없다. 이 값을 확률로 표기하지 않는다.

### 7.3.3 퍼센트 카드 (2026-08-05 추가)

사용자 요청으로 백분율 카드 2종을 만든다. **§7.3.2의 "확률로 표기하지 않는다"와 정면으로 부딪히므로, 표기 조건을 여기서 못 박는다.**

| 카드 | 뜻 | 구성 축 (가중치) |
| --- | --- | --- |
| 상대도 마음이 있을 신호 | 상대가 이쪽으로 얼마나 기울어 있는가 | 기울기 방향(3) · 상대 선톡(2) · 상대 질문(2) · 상대 응답(2) · 상대 이모티콘 정서(1) |
| 더 이어질 신호 | 대화가 계속 굴러갈 여지 | 주고받는 균형(3) · 대화 끊김 없음(2) · 서로 물어봄(2) · 분량 균형(1) · 대화량 감소 없음(2) |

```
raw = Σ(축값 × 가중치) / Σ(가용 축의 가중치)          // 0~1
값  = 50 + 50 × tanh((raw − 0.5) × 4)                // 0~100
```

**배율 4를 쓰는 이유.** 축이 전부 "0.5 근처 비율"이라 여럿을 평균하면 값이
가운데로 뭉친다(평균으로의 회귀). 실측(대화 6종): 기울기는 60점, `더 이어질`은
63점 벌어지는데 `상대도 마음이 있을 신호`는 **22점**뿐이었다 — 그 폭으로는
카드가 대화를 구별해 말하지 못한다. 배율을 넣으면 41점으로 벌어진다.

`tanh`을 쓰는 것은 아무리 키워도 0~100을 벗어나지 않고 끝에서 완만해져
극단이 잘리지 않기 때문이다. **단조 변환이라 대화 사이 순서는 바뀌지 않는다** —
없는 정보를 만드는 것이 아니라 있는 차이를 펴는 것이다(`SYNC_SCALE`과 같은 계열).

**표기 조건 — 하나라도 빠지면 이 카드를 내보내지 않는다.**

1. 구성 축 전부를 값·가중치·출처와 함께 화면에 편다 (`73% = 이 다섯 개를 이렇게 섞은 값`)
2. 고정 문구 — `맞을 확률이 아닙니다. 아래 지표를 가중 평균해 100점으로 옮긴 값입니다.`
3. 결측 축은 **0으로 채우지 않고 가중치에서 뺀 뒤 재정규화**한다. 0.5(중립)로 채우면 축 하나만 살아 있어도 값이 50 근처로 뭉개져 대화끼리 구별이 안 된다
4. `precisionReduced`면 **5단위로 반올림**한다. 22건 표본에 `73%`는 없는 정밀도를 주장하는 것이다(§6.4와 같은 취지)
5. 카드 이름에 "확률"을 쓰지 않는다. `신호`로 쓴다

**LLM은 이 값을 만들지 않는다.** `MODELS §4.2` 규칙 7과 `verify.ts`의 금지어 `확률`은 그대로 둔다 — 해석 문단이 스스로 확률을 지어내는 것과, 여기서 공개된 식으로 계산해 카드로 보여주는 것은 다른 일이다.

> **미해결**: `PRD §5 Out`은 "성사 확률 예측"을 범위 밖으로 두고 있다. PRD는 D1 이후 변경 금지라 여기서 고치지 않았다. 카드 이름을 `신호`로 유지하는 한 예측이 아니라 지수이므로 형식적으로는 어긋나지 않으나, 사용자에게 어떻게 읽히는지는 별개 문제다.

### 7.4 근거 배지

| 모드 | 표시 |
| --- | --- |
| txt | `메시지 12,480개 중 최근 120개로 산출 · 8개월 · 세션 412개` |
| 캡처 | `메시지 42개 · 캡처 5장 구간 · 표본 낮음` |

## 8. 심화 지표 (B급, txt 전용, scope: full)

### 8.1 순수 선톡률

세션 첫 메시지 비율. 단 **아침 이어받기 제외.**

**기상 프록시**: 화자별 04~12시 메시지 시각의 5퍼센타일.
- 최소 표본: 해당 시간대 **30건 이상 && 관측 14일 이상**
- 미달 시 프록시 비활성 → 보정 없이 집계하고 카드에 "기상 보정 미적용" 표시 (야근·교대근무 붕괴 방어)
- 판정: 세션 시작이 기상 프록시 +2h 이내 && 직전 세션이 전날이면 **아침 이어받기**

### 8.2 무응답률

```
무응답률 = (내 버스트로 끝난 세션 중, 다음 세션도 내가 시작했거나 다음 세션이 없는 수)
           / (내 버스트로 끝난 세션 수)
```

**시간 임계값을 쓰지 않는다.** 세션 구조만으로 정의하므로 6시간 기준과 충돌하지 않는다. 6시간 후 상대가 답하면 자동으로 "상대 선톡 세션"이 되어 무응답이 아니게 되고, 선톡률과 해석이 일관된다.

### 8.3 응답 분포

전환 쌍의 간격. **3버킷: ≤5분 / ≤1시간 / ≤6시간.** 6시간 초과는 정의상 새 세션이므로 버킷이 없다.

**중앙값을 쓰지 않는다.** 타임스탬프가 분 단위 해상도라 활발한 대화에서 0으로 수렴한다.

### 8.4 월별 온도 / 변화점

| 기간 | 처리 |
| --- | --- |
| 12개월 이상 | 월별 + 3개월 이동평균, 최대 낙폭 1지점 |
| 6~12개월 | 월별 + 2개월 이동평균 |
| 3~6개월 | 주별, 변화점 표시 안 함 |
| 3개월 미만 | 섹션 숨김 |

변화점 라벨 고정 캡션: **"이 시점에 무슨 일이 있었는지는 데이터가 알지 못합니다."**

### 8.5 말버릇 대조

빈도가 아니라 **격차**로 뽑는다. 로그 오즈비 + 디리클레 사전:

```
z(w) = log((f_A + α) / (N_A + αV - f_A - α)) - log((f_B + α) / (N_B + αV - f_B - α))
α = 0.01
```

- n-gram 2~4글자
- 필터: 두 사람 **합계 10회 이상** & 각자 1회 이상
- **부분집합 제거**: 짧은 n-gram 빈도가 이를 포함하는 긴 n-gram 빈도의 80% 이상이면 짧은 쪽 삭제 (`는데`/`그런데` 중복 해결)
- 불용어 40개 하드코딩 (`는데`, `니까`, `습니`, `어서`, `으로`, `에서`, `하고` …)
- 표본 하한: **각자 200개 이상**

## 9. C급 지표 (캡처 전용)

`affect`는 Vision 2패스 산출물. **txt에서는 구조적으로 계산 불가**이며, 이것이 캡처 입력의 존재 이유다.

### 9.1 이모티콘 온도차

```
score(m) = m.affect.valence × m.affect.intensity
온도차 = mean(score, who='me') - mean(score, who='other')
```

−2.0 ~ +2.0 → 표시용 −100 ~ +100 정규화. 표본 하한: 이모티콘 **8개**.

### 9.2 이모티콘 정서 다양도

```
다양도 = stdev(valence) × (고유 emojiDesc 수 / 전체 이모티콘 수)
```

한 종류만 반복하는 쪽은 형식적으로 쓰는 것이다. 화자별로 계산해 대비 표시.

### 9.3 헤드라인에 넣지 않는다

C급은 **별도 카드로만** 노출한다. Vision 정서 판독이 흔들려도 기울기가 흔들리지 않게 하는 방어선이다.

## 10. 임베딩 지표

`MODELS.md` §3 참조. 공식만 여기 둔다.

### 10.1 전처리

**2글자 이하 반응(`ㅇㅇ`, `ㅋㅋ`, `네`, `ㅎㅎ`)은 제외한다.** 어느 관계에나 대량으로 존재하여 두 사람의 벡터를 같은 지점으로 끌어당긴다. 이 전처리 없으면 분리도 축이 무너진다.

### 10.2 동조율

```
동조_나   = mean(cos(v[상대 버스트 마지막], v[내 첫 응답]))
동조_상대 = mean(cos(v[내 버스트 마지막],   v[상대 첫 응답]))
I_동조 = norm(동조_나, 동조_상대)
```

두 값의 차이가 **누가 상대에게 맞춰주는가**다. 답장은 빠른데 동조율이 낮은 조합이 리포트에서 가장 서늘한 부분이다.

### 10.3 말투 분리도

```
분리도 = ‖centroid_me − centroid_other‖ / mean(그룹 내 분산)
```

0~100 정규화. 낮으면 말투 수렴(오래 붙어 지낸 관계), 높으면 서로 다른 방식으로 말함. **대칭 지표이므로 기울기 축이 아니라 상태 카드다.**
