## 1. 사용 순간

새벽 1시. `ㅇㅇ 알겠어` 하나를 받았다. 이게 무슨 뜻인지 모르겠다.

이 순간의 사용자는 **리포트를 원하지 않는다.** 자기가 지금 이 관계에서 어느 쪽에 서 있는지, 숫자 하나로 알고 싶어 한다.

입력이 두 개인 이유도 이 순간에서 나온다.

- **캡처**는 그 순간 쓸 수 있는 유일한 입력이다. 새벽 1시에 대화 내보내기를 하는 사람은 없다
- **txt**는 제대로 재보고 싶을 때의 입력이다

가장 흔한 사용 맥락은 **아직 확정되지 않은 관계**다. 사귀는 사이도 아니고 그냥 친구도 아닌 구간에서, 자기가 어느 쪽에 서 있는지가 가장 안 보인다. 그래서 관계 유형에 `crush`를 둔다.

이 정의가 잘라내는 것 넷:

| 유혹 | 자름 |
| --- | --- |
| 지표를 여러 개 나열하고 싶다 | 헤드라인은 숫자 **하나** |
| 답장 문구를 대신 써주고 싶다 | 관찰만 한다. 처방하지 않는다 |
| 관계가 좋다/나쁘다 말하고 싶다 | 기울기는 **방향**이지 평가가 아니다 |
| **"이어질 확률"을 말하고 싶다** | **정답 라벨이 없어 계산 불가. 지금 신호만 보여준다** |

## 2. 문제 정의

### 2.1 내보내기 txt는 손실 포맷이다

카카오톡 대화 내보내기의 실제 출력:

```
2026년 7월 11일 오전 10:53, 상대 : 사진
2026년 7월 11일 오전 10:54, 나 : 그래서 오늘 좀 힘들었어
2026년 7월 11일 오전 10:58, 상대 : 이모티콘
```

**3개 중 2개가 플레이스홀더다.** 어떤 사진이었는지, 어떤 이모티콘이었는지 정보량이 0이다. 관계의 정서가 가장 많이 담기는 신호가 정확히 그 자리에서 소실된다.

*(실측: PC 내보내기 23,465개 메시지 중 `사진`·`이모티콘` 플레이스홀더 1,186개)*

### 2.2 진입 장벽

내보내기 기능의 위치를 아는 사용자가 거의 없다. 캡처는 모두가 이미 할 수 있다.

### 2.3 우리가 푸는 것

1. 내보내기에서 지워진 정서 신호를 **캡처에서 복원**한다
2. 어휘 겹침으로 계산할 수 없는 관계 지표를 **의미 공간에서 계산**한다
3. 표본이 부족하면 **부족하다고 말한다**

## 3. 입력 비대칭 원칙

> **txt** — 시간축은 완전하고 내용이 손실됨
> **캡처** — 내용은 완전하고 시간축이 조각남

정확히 반대다. **어느 쪽도 상위 집합이 아니다.** 캡처는 txt의 열등한 버전이 아니며, 지표 설계 전체가 이 비대칭 위에 세워진다.

### 3.1 필드 가용성 — 모든 지표 가용성이 여기서 파생된다

| 필드 | txt | 캡처 |
| --- | --- | --- |
| `who` (화자) | ○ 제목 줄 추론 | ○ 좌우 정렬 (더 확실) |
| `time` (시:분) | ○ 전부 | △ 일부 (같은 분 연속 발화는 마지막만 표시) |
| `date` (날짜) | ○ 전부 | △ 날짜 구분선이 잡힐 때만 |
| `text` | ○ | ○ |
| `type` | ○ | ○ |
| `affect` (정서 좌표) | **✕ 구조적 불가** | ○ |
| 시간축 연속성 | ○ 전 구간 | ✕ 조각 |
| 누락 없음 보장 | ○ | ✕ |

### 3.2 지표 등급

| 등급 | 정의 | 대표 |
| --- | --- | --- |
| **A급** | 세션 없이 성립 (양쪽 공통) | 메시지수·길이·질문·동조율·말투 분리도 |
| **B급** | 시간축 연속성 필요 (txt 전용) | 선톡률·무응답률·월별 온도·변화점·말버릇 |
| **C급** | 정서 좌표 필요 (캡처 전용) | 이모티콘 온도차·이모티콘 정서 다양도 |

**C급의 존재가 캡처 입력의 존재 이유다.** §2.1에서 "지워진 걸 복원했다"고 말하려면 실제로 복원한 지표가 화면에 있어야 한다.

### 3.3 판독 창 — 두 경로를 화해시키는 장치

```
판독 창 = 가장 최근 메시지 120개
```

- **txt** → 헤드라인은 최근 120개만 잘라 계산. 나머지는 심화 지표에서만 사용
- **캡처** → 읽어낸 전부(통상 30~60개). 120개 미달 비율이 신뢰도에 반영

헤드라인 축이 세션을 요구하지 않으므로, 창만 맞추면 두 경로가 **같은 정의·같은 표본 크기**로 계산된다. 캡처 모드에서 헤드라인 지표를 교체할 필요가 없다.

부수 효과: 임베딩 대상이 120개로 제한되어 **프라이버시 노출량이 함께 줄어든다.**

## 4. 설계 원칙

### 4.1 모델은 데이터를 만들 수 있다. 판정은 못 한다.

| 층 | 역할 | 지표 생성 | 규칙 기반 대체 | 결정론성 |
| --- | --- | --- | --- | --- |
| **Vision** | 유실 데이터 복원 (전사 + 정서 좌표) | 예 | **불가** | temp 0, 캐시로 고정 |
| **임베딩** | 좌표 제공 (거리는 코드가 계산) | 예 | **불가** | 완전 결정론 |
| **통계** | 수치 계산 | 예 | — | 완전 결정론 |
| **LLM** | 문장 서술 | **아니오** | 가능 | 비결정론 |

**Vision과 임베딩에 폴백이 없다는 것이 곧 정당성의 증거다.** 이모티콘 그림에서 정서를 읽는 규칙 기반 방법은 존재하지 않는다.

LLM만 데이터 생성 권한이 없고, 이 경계는 §MODELS 수치 대조 검증으로 **코드가 강제한다.**

### 4.2 지표는 입력 모드가 아니라 필요 필드에 매달린다

```
입력 모드 → 필드 가용성 → 지표 가용성
```

지표 계산 코드에 `if (mode === 'capture')`가 들어가는 순간 두 경로가 다르게 표류한다. 경로 차이는 **오직 필드 결측으로만** 표현한다.

### 4.3 표본 부족을 값으로 위장하지 않는다

세션 3개 중 3개를 100%로 쓰지 않는다. 축소 추정으로 당기고, 하한 근처면 소수점을 버린다.

### 4.4 못 읽은 신호는 조용히 버린다

결측 목록을 나열하지 않는다. 잠긴 카드 한 장과 각주 한 줄로만 남긴다.

### 4.5 낮은 기울기에서도 사람을 밀어내지 않는다

"가망 없음", "포기" 같은 어휘를 템플릿과 프롬프트에서 전면 금지한다. 기울기는 **이 대화의 신호에 대한 관찰**이지 사람에 대한 판정이 아니다.

| 항목 | 이유 |
| --- | --- |

## 6. 결과 화면

**두 입력이 완전히 같은 화면을 쓴다.** 차이는 카드 상태와 각주뿐이다.

| # | 섹션 | 비고 |
| --- | --- | --- |
| 1 | **처리 과정** | 단계별 진행 노출. "API 한 번 호출이 아니다"를 전달하는 유일한 화면 |
| 2 | **기울기 게이지** | + 한 줄 판정 + 근거 배지 + **"N개 축 중 M개로 산출"** |
| 2-1 | 신호 요약 | **썸 모드에서만.** 0~100 + 구성 축 + "예측이 아닙니다" 고정 문구 (SPEC §7.3.2) |
| 3 | **지표 카드** | 나 vs 상대 대비. `OK` / `LOCKED` / `INSUFFICIENT` 3상태 |
| 4 | 이모티콘 정서 대조 | **C급 — 캡처 모드에서만 값을 가짐** |
| 5 | 월별 온도 그래프 | B급 — txt·3개월↑ |
| 6 | 말버릇 대조 | B급 — 화자당 200개↑ |
| 7 | 명장면 | 클라이언트 전용, LLM 미전송 |
| 8 | **LLM 한 문단** | 스켈레톤 → 스트리밍 |
| 9 | 하단 고정 문구 | 아래 |

> 이 수치는 메시지 패턴이며, 애정의 크기가 아닙니다. 전화·만남·다른 메신저는 여기에 없습니다.

**숫자를 먼저 다 보여주고 해석을 맨 끝에 둔다.** 이 순서면 LLM이 조금 무례해도 근거가 이미 화면에 있어 불쾌하지 않다.

### 6.1 잠긴 카드를 숨기지 않는다

| 상태 | 표현 | 문구 |
| --- | --- | --- |
| `OK` | 값 표시 | — |
| `LOCKED` | 회색 + 자물쇠 | "전체 대화 파일을 넣으면 열립니다" |
| `INSUFFICIENT` | 회색 | "메시지가 더 필요합니다 (87 / 200)" |

없는 것보다 잠긴 것이 낫다. 결함이 아니라 **다음 행동 유도**가 되고, 두 입력이 서로를 보완하는 구조가 화면에서 그대로 보인다.

### 6.2 낮은 기울기 전용 처리

게이지를 붉게 하지 않는다(회색 계열). 판정 문장을 행동 지시가 아니라 여유 문장으로 쓴다.

## 7. 프라이버시

### 7.1 모드별 배지 (상단 고정, 통합 문구 금지)

| 모드 | 배지 |
| --- | --- |
| txt | **기기에서 파싱됨** — 대화 원문 전체는 서버에 전송되지 않습니다. 의미 분석을 켜면 최근 120개 메시지만 전송됩니다 |
| 캡처 | **이미지는 분석 후 즉시 폐기 · 저장 안 함** — 전사 결과는 이 브라우저에만 저장됩니다 |

문구가 모드별로 다른 것 자체가 정직성의 증거다.

### 7.2 구현

| 요구 | 구현 |
| --- | --- |
| 원문 미보관 | txt는 Worker에서 파싱, 집계만 반환. 이미지는 메모리 처리 후 즉시 파기 |
| 이름 미수집 | Vision이 발신자 이름을 전사하지 않음. txt 표시명은 즉시 `A`/`B` 치환 |
| 서버 무상태 | 캐시는 IndexedDB(클라이언트)만 |
| 임베딩 옵트인 | txt 모드에서 체크박스. 끄면 동조율·분리도 축만 빠지고 나머지 정상 |
| 노출 최소화 | 임베딩 대상 = 판독 창 120개 (전체 아님) |
| 레이트 리밋 | **리포트 단위** IP당 분당 3회. 데모용 바이패스 키 |

### 7.3 상대방 동의 — 발표 대응

1. 본인이 참여한 대화 기록의 열람권 범위로 본다
2. 그래서 원문을 서버에 남기지 않는 구조로 설계했다
3. 남는 한계를 알기에 **상대 이름은 수집·표시하지 않는다** *(실제 구현)*

## 9. 일정

### D0 — 검증 (1.5시간)
`TESTPLAN.md` 체크리스트 수행. 실파일 개행 재확인, 실물 캡처 1세트 VLM 전사 테스트, 다크모드 1장, 렌더러 채택 여부 결정.

### D1 — 지표 엔진 + 이미지 파이프라인
공통 스키마 · 지표 레지스트리 · Vision 1패스(전사) · 겹침 제거 · Vision 2패스(정서) · IndexedDB 캐시 · 캡처 시드 3종
**종료 조건: 캡처 시드 3종이 서로 다른 밴드를 출력**

### D2 오전 — txt 어댑터
PC/안드 파서(Worker, 캐리 버퍼) · 화자 병합 UI · 세션/버스트 · 골든 테스트 통과

### D2 오후 — 리포트 화면
처리 과정 · 게이지 · 3상태 카드 · C급 카드 · 프라이버시 배지

### D3 오전 — 임베딩 축 + LLM
동조율·분리도(4번째 축, 옵셔널) · LLM 해석 · **수치 대조 검증** · 모드별 폴백

### D3 오후 — 방어·리허설
경로 일치성 테스트 · 입력 거부 · 바이패스 키 · **리허설 2회**

**임베딩을 D3에 두는 이유**: 헤드라인 4번째 축이자 옵셔널이라, 실패하면 3축으로 자동 축소된다(§4.2 규칙의 실전 이득). 일정 리스크가 가장 낮은 위치.

### 우선순위

| 등급 | 항목 |

| **반드시** | 3축 헤드라인 · 판독 창 · 3상태 카드 · 하드 플로어 · LLM 폴백 · C급 카드 1개 |

## 10. 데모

**준비물**: txt 시드 3종 · 캡처 시드 3종 · 다크모드 사전 테스트 · 바이패스 키 주입

1. 캡처 세트 1개로 전체 흐름 — **처리 과정 화면이 보이는 것이 핵심**
2. 이모티콘 정서 카드 → **"내보내기가 지운 걸 여기서 복원했습니다"**
3. 시드 3종 결과 대조 — "같은 도구, 다른 판정"
4. txt로 전환 → **잠겨 있던 카드가 열리는 것** 시연
5. LLM 폴백 강제 토글 — "LLM이 죽어도 리포트는 산다"
6. **맨 마지막**: 심사위원 즉석 캡처

즉석 입력을 앞에 두지 않는다. 실패 시 시드 캡처로 즉시 전환.

### 발표 문장

> 카카오톡 내보내기는 이모티콘과 사진을 텍스트 한 단어로 지웁니다. 그 지워진 부분을 캡처에서 복원했습니다.

> 앞의 두 모델이 데이터를 만들고, 마지막 모델은 그 데이터를 설명만 합니다. 숫자를 만들 권한은 앞의 둘에만 있고, 그건 코드로 강제합니다.

> 캡처는 데이터가 적습니다. 그래서 적은 데이터로도 답할 수 있는 질문만 답하게 했습니다.

## 부록 A. 결정 로그

| # | 결정 | 근거 |
| --- | --- | --- |
| D-01 | 캡처를 txt와 대등한 입력으로 취급 | 캡처에만 존재하는 정보(이모티콘 정서)가 있어 대체 경로가 아님 |
| D-02 | 지표를 입력 모드가 아닌 필요 필드에 매달기 | 모드 분기가 지표 코드에 침투하는 것을 차단 |
| D-03 | 헤드라인 축을 곱셈 분해 (메시지수 × 길이) | 총 글자수와 버스트당 메시지는 구조적 이중 계상 |
| D-04 | 캡처 모드에서 헤드라인을 교체하지 **않음** | 3축이 세션을 요구하지 않으므로 판독 창만 맞추면 그대로 성립 |
| D-05 | 판독 창 120개 도입 | 표본 크기 차이가 경로 간 값 차이의 근본 원인 |
| D-06 | 없는 축을 0으로 채우지 않고 재정규화 | 0은 "균형"을 뜻해 결측이 방향을 왜곡 |
| D-07 | 잠긴 지표를 숨기지 않고 노출 | 결함이 아니라 다른 입력 유도 장치 |
| D-08 | LLM에 지표 생성 권한 미부여 + 수치 대조 강제 | 프롬프트는 지키다 말 수 있고 대조는 못 어김 |
| D-09 | 임베딩을 옵트인 + 판독 창으로 제한 | 브라우저 파싱 프라이버시 서사를 포기하지 않기 위해 |
| D-10 | 브라우저 파싱 **유지** (포기 안 함) | 임베딩 대상을 120개로 줄이면 옵트인으로 성립. txt 경로의 최대 무기를 버리지 않는다 |
| D-11 | 카카오 API는 출력(나에게 보내기)에만 | 대화 조회 API 부재 확인 |
| D-12 | txt는 PC + 안드로이드 둘 다 지원 | CRLF 레코드 분리 발견으로 추가 비용이 정규식 세트 하나 |
