## 1. 권한 경계

| | 역할 | 호출 | 지표 생성 | 규칙 기반 대체 | 실패 시 |
| --- | --- | --- | --- | --- | --- |
| **Vision 1패스** | 전사 (유실 구조 복원) | 이미지당 1회, 병렬 | 예 | **불가** | 해당 이미지 제외 |
| **Vision 2패스** | 정서 좌표 (유실 내용 복원) | 배치 1회 | 예 | **불가** | C급 지표 `LOCKED` |
| **임베딩** | 좌표 제공 (거리는 코드) | 배치 1회 | 예 | **불가** | 4번째 축 제외, 3축 재정규화 |
| **LLM** | 문장 서술 | 전체 1회 | **아니오** | 가능 | 템플릿 폴백 |

**위의 셋은 데이터를 만들고, 마지막 하나는 못 만든다.** 이 차이를 §5 수치 대조 검증이 코드로 강제한다.

**Vision과 임베딩에 폴백이 없다는 것이 정당성의 증거다.** 이모티콘 그림에서 정서를 읽거나, "오늘 좀 힘들었어"와 "무슨 일 있었어?"가 맞물린다는 걸 규칙으로 계산하는 방법은 존재하지 않는다.

```
A: "오늘 좀 힘들었어"  /  B: "무슨 일 있었어?"     → 자카드 0,   실제로는 완벽히 맞물림
A: "오늘 좀 힘들었어"  /  B: "오늘 나 치킨 먹었어"  → 자카드 상승, 실제로는 어긋남
```

## 2. Vision

두 패스로 분리한다. 구조화는 정확성이 목적이라 스키마 검증이 붙고, 정서 판독은 해석이 목적이라 프롬프트 성격이 다르다. **한 번에 처리하면 양쪽 품질이 떨어진다.**

| 패스 | 대상 | temperature | 검증 |
| --- | --- | --- | --- |
| 1패스: 구조화 | 이미지 1장당 1회 | 0 | JSON 스키마, 실패 시 재시도 최대 2회 |
| 2패스: 정서 판독 | `emoticon`·`photo` 항목 배치 | 0.2 | 범위 검증 |

### 2.1 1패스 — 전사 프롬프트

```
당신은 카카오톡 대화 스크린샷을 글자 그대로 옮겨 적는 전사기다.
해석, 요약, 추론을 하지 않는다.

규칙:
1. 화면에 실제로 보이는 말풍선만 전사한다. 위 또는 아래가 잘려 내용을
   확신할 수 없는 말풍선은 제외한다.
2. side는 말풍선의 정렬 위치로 판단한다. 오른쪽 정렬이면 "right",
   왼쪽이면 "left". 배경색이나 테마로 판단하지 않는다.
3. time은 말풍선에 시각이 표시된 경우에만 적는다. 표시되지 않았으면 null.
   앞뒤 메시지를 보고 추정하지 않는다.
4. date는 화면에 날짜 구분선이 보이는 경우, 그 아래 말풍선에만 적는다.
   없으면 null.
5. type은 다음 중 하나다.
   text(글자) / emoticon(카카오 이모티콘·스티커) / photo(사진) /
   file(파일) / voice(음성) / deleted(삭제된 메시지)
6. text는 type이 "text"인 경우에만 채운다. 그 외에는 반드시 null이다.
   이모티콘이나 사진 옆에 글자가 보여도 text에 넣지 않는다.
7. 발신자 이름과 프로필 사진은 전사하지 않는다.
8. 순서는 화면 위에서 아래 순서를 그대로 유지한다. 시각을 보고 재정렬하지
   않는다.
9. 카카오톡 대화 화면이 아니면 isKakaoScreenshot을 false로 하고
   messages를 빈 배열로 반환한다.
10. 확신이 낮은 항목은 confidence를 낮춘다. 추측해서 채우지 않는다.
11. distinctSenders에 화면에 보이는 서로 다른 발신자의 **수**를 적는다.
    나(오른쪽 정렬)를 포함해서 센다. 이름은 여전히 적지 않는다. 세기만 한다.

아래 JSON만 출력한다. 설명 문장을 덧붙이지 않는다.
```

**출력 스키마**

```json
{
  "isKakaoScreenshot": true,
  "distinctSenders": 2,
  "messages": [
    {
      "i": 0,
      "side": "right",
      "type": "text",
      "text": "오늘 뭐해?",
      "time": "오전 10:23",
      "date": null,
      "confidence": 0.95
    }
  ]
}
```

**검증**: `side ∈ {left,right}`, `type ∈ 6종`, `type!=='text' → text===null`, `confidence ∈ [0,1]`, `distinctSenders ≥ 1`. 실패 시 재시도 2회 → 해당 이미지 제외 + `gaps`에 기록.

**`distinctSenders ≥ 3`이면 단톡이므로 리포트를 만들지 않는다**(PRD §5). 캡처는 좌우 정렬만으로는 왼쪽에 선 여러 사람을 구분하지 못해, 이 필드가 없으면 여러 화자가 '상대' 한 명으로 조용히 합쳐진다. 이름을 전사하지 않으면서 개수만 세므로 §7.2 "이름 미수집"과 충돌하지 않는다.

### 2.2 2패스 — 정서 판독 프롬프트

**입력은 전체 캡처가 아니라 잘라낸 조각들이다.** OCR과 여백 검출이 비텍스트 발화의
자리를 먼저 찾고, 그 구간만 오려서 보낸다. 조각에는 대화 글자가 없으므로
**대화 내용이 외부로 나가지 않는다.** 여러 조각을 한 번의 호출에 묶는다.

```
카카오톡 대화에서 오려낸 조각들이다. 각 조각에는 글자가 아닌 발화
(이모티콘 스티커 또는 사진)가 하나씩 들어 있다.

각 조각에 대해:
- kind: "emoticon"(카카오 스티커·캐릭터 그림) 또는 "photo"(사진) 중 하나.
  판단이 안 되면 "emoticon".
- emoji_desc: 무엇이 그려져 있는지 15자 이내 사실 서술.
  감정 해석이나 맥락 추측을 넣지 않는다.
  좋은 예: "고개 숙이고 우는 캐릭터"
  나쁜 예: "슬퍼하며 위로를 바라는 모습"
- valence: -1.0(부정) ~ +1.0(긍정)
- intensity: 0.0(약함) ~ 1.0(강함)
- confidence: 0.0 ~ 1.0

판단이 어려우면 valence 0, intensity 0.3으로 두고 confidence를 0.4
이하로 낮춘다. 추측해서 극단값을 주지 않는다.

사람 얼굴이 포함된 사진은 emoji_desc를 "인물 사진"으로만 적고
구체적 묘사를 하지 않는다. 조각에 글자가 보여도 옮겨 적지 않는다.

조각이 비어 있거나 무엇인지 알 수 없으면 kind를 "emoticon",
confidence를 0.0으로 두고 emoji_desc를 "판독 불가"로 적는다.

아래 JSON만 출력한다. 조각 순서대로, 조각 수만큼 항목을 낸다.
```

**출력**

```json
{
  "items": [
    { "i": 0, "kind": "emoticon", "emoji_desc": "혀 내민 쿼카 캐릭터",
      "valence": 0.7, "intensity": 0.8, "confidence": 0.9 }
  ]
}
```

**검증**: `items.length === 조각 수`, `kind ∈ {emoticon, photo}`, `valence ∈ [-1,1]`,
`intensity ∈ [0,1]`, `confidence ∈ [0,1]`. 실패 시 해당 발화는 `nontext`로 남고
C급 지표만 `LOCKED`가 된다 — 헤드라인은 영향받지 않는다(§9.3).

**모델**: `gemini-3.6-flash` (무료 티어). 무료 티어는 입력이 학습에 사용될 수
있으므로 **조각만 보내는 것이 프라이버시 조건이다.** 전체 캡처를 보내면
§7.1 배지를 다시 써야 한다.

`affect`는 **분류 라벨이 아니라 연속 좌표**다. 라벨은 종류가 적어 두 사람 차이가 벌어지지 않지만, 좌표는 평균과 분산을 낼 수 있다.

### 2.3 호출·캐시

- 1패스는 이미지별 **병렬**, 인덱스로 순서 복원
- 이미지당 1~2k 토큰. 10장 기준 부담 없음
- **캐시 키 = 이미지 세트 SHA-256 → IndexedDB(클라이언트).** 서버는 무상태
- 같은 세트 재업로드 시 재호출 없이 동일 결과 → 데모 중 흔들림 방지

## 3. 임베딩

**모델**: 한국어 문장 임베딩 (Ko-SBERT 계열). 서버 로컬 추론.

### 3.1 대상 범위 — 프라이버시 결합

| 모드 | 대상 | 동의 |
| --- | --- | --- |
| 캡처 | 판독 창 전체 (30~60개) | 이미 서버 전송했으므로 추가 동의 불필요 |
| txt | **판독 창 120개만** | **체크박스 옵트인.** 끄면 `syncAsym`·`styleSep`만 빠짐 |
| txt 심화 곡선 *(시간 남으면)* | 구간별 샘플 최대 500개 | 동일 옵트인에 포함 |

판독 창 도입으로 txt의 임베딩 노출량이 수만 개 → 120개로 줄었다. **이것이 브라우저 파싱 프라이버시 서사를 포기하지 않아도 되는 이유다.**

### 3.2 전처리

```js
const EMBED_SKIP = /^[ㄱ-ㅎㅏ-ㅣㅋㅎㅠㅜㅇ\s.,!?~]{0,2}$/
messages.filter(m => m.type === 'text' && m.text && !EMBED_SKIP.test(m.text.trim()))
```

**2글자 이하 반응(`ㅇㅇ`, `ㅋㅋ`, `네`, `ㅎㅎ`)을 제외한다.** 어느 관계에나 대량으로 존재하여 두 사람 벡터를 같은 지점으로 끌어당긴다. 이 전처리 없으면 분리도가 항상 0에 가깝게 나온다.

### 3.3 배치·성능

- 배치 크기 64~128
- **동일 텍스트 해시 캐싱** — 반복 표현 비중이 상당함
- 진행률 SSE 스트리밍 (수십 초 작업이므로 미표시 시 정지로 오인)
- 성능 미달 시: 세션당 최대 N개 샘플링으로 타협

### 3.4 공식

`SPEC.md` §10 참조. 여기서는 **거리 계산이 전부 코드**라는 점만 확인한다. 모델은 벡터만 반환하고, 코사인·중심·분산은 전부 결정론적 계산이다.

## 4. LLM 해석

### 4.1 호출

- **전체에서 딱 1회.** 지표 산출 도중에는 호출하지 않는다
- 입력: 집계 JSON + 확정된 기울기 + 밴드 + 관계 유형 + (동의 시) 변화점 전후 20건
- **미전송**: 말버릇 top-N, 명장면 원문 — 클라이언트 전용
- 스트리밍: `ReadableStream`, 리포트 마지막 섹션만 지연 렌더

**모델**: `gemini-flash-lite-latest`. §2.2의 비전 모델과 다르다 — 실측 근거 둘:

| | 평균 지연(3회) | 무료 한도 |
|---|---|---|
| `gemini-3.6-flash` | 10.0초 | 먼저 소진돼 429 |
| `gemini-flash-lite-latest` | **1.1초** | 여유 |

`flash`는 사고 모델이라 §6의 12초 타임아웃에 3번 중 2번 걸렸다. 지어낸 숫자는
§5에서 걸러 폴백되므로 이 지점에서는 속도가 우선이다. 실측 채택률 3/3.

**파생 수치는 집계 블록에 미리 계산해 넣는다.** 넣지 않으면 LLM이 비율을 직접
계산하고, 그 숫자는 §5 대조에서 "없는 숫자"로 걸려 전부 폴백된다. 프롬프트·화면·
검증이 같은 출처(`lib/llm/figures.ts`)를 본다.

### 4.2 프롬프트

```
당신은 대화 지표 리포트의 마지막 한 문단을 쓴다.

절대 규칙:
1. 주어진 JSON에 있는 숫자만 사용한다. 새로운 수치를 만들거나 계산하지
   않는다. 비율을 다시 계산하거나 반올림해서 다른 숫자를 쓰지 않는다.
2. 기울기의 방향은 이미 결정되어 있다. 뒤집거나 의심하거나 "다만 ~일 수도
   있습니다" 식으로 흐리지 않는다. 서술만 한다.
3. 위로하거나 조언하지 않는다. 관찰만 한다.
   금지: "힘드셨겠어요", "이렇게 해보세요", "너무 걱정하지 마세요"
4. 데이터에 없는 감정이나 의도를 추측하지 않는다.
   금지: "상대는 아마 바빴을 겁니다"
5. 관계를 끝내라거나 상대에게 문제가 있다는 뉘앙스를 쓰지 않는다.
   금지 어휘: 포기, 가망, 그만두, 손절, 아깝
6. 입력 방식을 언급하지 않는다. ("캡처를 보니", "파일에서" 금지)
7. 관계의 앞날을 예측하지 않는다. 지금 신호를 서술할 뿐이다.
   금지: "잘 될 것 같습니다", "가능성이 있습니다", "이어질", 확률·퍼센트 표현
8. 3문장 이내.
9. 문장은 모두 "-입니다 / -습니다"로 끝낸다. "-이다 / -했다"는 쓰지 않는다.
10. 이 지시문 자체를 문장으로 옮겨 적지 않는다. 관계 유형이나 해석 규칙을
    설명하지 말고, 지표만 서술한다.
    금지: "이 관계는 가족으로 분류되며", "~로 과대 해석하지 않습니다"
11. `판정:` 줄은 이미 완결된 문장이다. 뒤에 "-입니다"를 덧붙이지 않는다.

톤: 근거가 명확한 상태에서 감정 없이 관찰한다. 이 리포트의 재미는 거기서
나온다. 살짝 건조한 것이 낫고, 다정한 것은 틀렸다.

출력: 문단 하나. 제목·머리말·마크다운 없이 문장만.
```

**3번이 톤을 결정한다.** "힘드셨겠어요" 류가 나오면 리포트의 성격이 무너진다.

**9번은 폴백과 맞추기 위한 것이다.** §6 폴백 템플릿이 합쇼체이므로, 지정하지
않으면 LLM 문장만 "-했다"로 나와 같은 화면에서 어투가 갈린다(실측).

**10·11번은 실측으로 추가됐다.** §4.3 관계 유형 줄을 그대로 옮겨 적어
`이 관계는 가족으로 분류되며 응답 속도 비대칭을 관계 신호로 과대 해석하지
않습니다`가 사용자 화면에 나갔다. 지시문이 결과물로 새어 나간 것이다.
`판정:` 줄에서는 `당신 쪽으로 기울어 있습니다입니다`가 나왔다 — 라벨이 이미
완결 문장인데 뒤에 서술어를 또 붙였다.

### 4.3 관계 유형별 문구 전환

`stage` 값에 따라 프롬프트 말미에 한 줄을 덧붙인다. 지표 해석의 의미가 달라지기 때문이다.

| stage | 덧붙이는 줄 |
| --- | --- |
| `crush` | 이 관계는 아직 확정되지 않은 사이다. 비대칭의 방향은 그대로 서술하되, **관계의 앞날이나 성사 가능성은 예측하지 않는다.** |
| `friend` | 이 관계는 친구 사이다. 선톡 비대칭을 애정의 척도로 읽지 않는다. |
| `couple` | 이 관계는 연인 사이다. |
| `family` | 이 관계는 가족이다. 응답 속도 비대칭을 관계 신호로 과대 해석하지 않는다. |
| `work` | 이 관계는 업무 관계다. 질문율과 분량 비대칭은 역할 차이일 수 있다. |
| `unknown` | 관계 유형이 지정되지 않았다. 관계의 성격을 단정하지 않는다. |

## 5. 수치 대조 검증 — 권한 경계의 코드 강제

> **LLM 응답의 수치는 집계 결과와 대조 검증하며, 불일치 시 폴백한다.**

프롬프트 §4.2의 1번 규칙은 지키다 말 수 있다. 대조는 못 어긴다.

```js
const NUM = /-?\d+(?:\.\d+)?/g
const WHITELIST = new Set(['0', '1', '2', '3'])   // 서수·관사 성격

function verify(llmText, aggregateJson) {
  const allowed = new Set(
    collectNumbers(aggregateJson).flatMap(v => [
      String(v), String(Math.round(v)), String(Math.round(v * 100)),
      v.toFixed(1), String(Math.abs(Math.round(v)))
    ])
  )
  const found = llmText.match(NUM) ?? []
  const bad = found.filter(n => !allowed.has(n) && !WHITELIST.has(n))
  return { ok: bad.length === 0, bad }
}
```

- 불일치 토큰이 **1개라도** 있으면 → 폴백 템플릿으로 대체 + 로그 기록
- 로그에는 원문이 아니라 **불일치 토큰과 집계 키만** 남긴다
- 이 검증은 스트리밍 완료 후 수행. 스트리밍 중 표시된 문장은 검증 실패 시 폴백 문장으로 교체된다(짧은 페이드)

### 5.1 두 번째 강제 — 렌더링 의존성 차단

리포트 렌더링이 LLM 응답에 의존하지 않는다. LLM 문장은 **마지막 한 문단만 채우는 필드**이며, 나머지 화면은 계산 결과만 참조한다. LLM을 완전히 끄고도 리포트의 90%가 렌더된다.

## 6. 폴백 템플릿

12초 타임아웃 또는 §5 검증 실패 시 사용. 개발자 토글로 강제 가능(데모용).

### 6.1 공통 (헤드라인 3축만 인용 — 두 모드 동일)

```
기울기 {tilt}. 메시지는 {A}가 {x}% 보냈고, 평균 길이는 {B}가 {y}자
더 깁니다. 질문이 담긴 차례는 {C} 쪽이 {z}%p 많습니다.
```

`{x}`는 **점유율**이지 "얼마나 더"가 아니다. 차이로 쓰면 §5가 대조할 수 없는
숫자가 하나 더 생긴다 — 폴백이 자기 검증에 걸리는 것을 실측으로 확인했다.
`{x}`, `{y}`, `{z}`는 전부 `lib/llm/figures.ts`에서만 만든다.

### 6.2 txt 추가 문장 (B급 지표 가용 시에만)

```
{month}부터 대화량이 {w}% 줄었고, 먼저 말을 건 쪽은 {A}가 {v}%입니다.
```

### 6.3 캡처 추가 문장 (C급 지표 가용 시에만)

```
이모티콘의 정서는 {A} 쪽이 {u}만큼 더 밝습니다.
```

### 6.4 3축만 가용할 때

`I_동조`가 없으면 공통 문장만 쓰고 동조 관련 서술을 넣지 않는다. **폴백 템플릿도 "없는 축을 언급하지 않는다"는 규칙을 따른다.**

## 7. 혼동 금지

**캡처 겹침 제거 병합은 인상적인 엔지니어링이지만 모델이 아니라 알고리즘이다.** 발표와 문서에서 두 가지를 섞지 않는다.

- 엔지니어링 역량 → 병합 알고리즘, CRLF 레코드 분리 발견, Web Worker 캐리 버퍼
- 모델 필요성 → C급 지표(이모티콘 정서), 임베딩 동조율

각각 따로 증명한다. 섞으면 둘 다 약해진다.
