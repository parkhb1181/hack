## 0. 왜 하네스를 먼저 잡는가

지표 계산기는 순수 함수라 네트워크 없이 검증할 수 있다.

```ts
computeStats(corpus: Corpus): Stats          // 모델 0, 네트워크 0 → 골든 테스트 가능
computeSemantic(corpus): Promise<Semantic>   // 네트워크 의존 → 목(mock) 필요
```

이 둘을 분리하지 않으면 통계 단위 테스트까지 임베딩 API에 묶인다. D1 종료 조건("시드 3종이 서로 다른 밴드")이 모델 가용성에 의존하면 검증이 아니라 도박이 된다.

## 1. D0 체크리스트 (1.5시간) — D1 착수 전 필수

### 1.1 txt 실파일 재확인

- [ ] 본인 1:1 대화를 **PC 카카오톡**에서 내보내기
- [ ] 본인 1:1 대화를 **안드로이드**에서 내보내기
- [ ] 두 파일의 개행 구조 확인 — `SPEC.md` §3.1 전제 재검증

```bash
python3 -c "
b=open('FILE','rb').read()
print('BOM:', b[:3]==b'\xef\xbb\xbf')
print('CRLF:', b.count(b'\r\n'), '| bare LF:', b.count(b'\n')-b.count(b'\r\n'))
"
```

> **판정 기준**: CRLF가 레코드 수준으로 존재하고 bare LF가 그보다 훨씬 적으면 통과.
> 만약 안드로이드가 LF-only로 바뀌었다면 `SPEC.md` §3.1을 즉시 수정하고 이어붙이기 로직을 주경로로 승격한다. **이 확인을 건너뛰면 D1이 통째로 날아간다.**

## 2. 시드 데이터 정의

| 시드 | 의도 | 기대 밴드 |
| --- | --- | --- |
| `seed_balanced` | 양쪽이 비슷하게 주고받음 | `even` |
| `seed_faded` | 초반 활발 → 후반 급감, 양쪽 다 줄어듦 | `even` (기울기는 균형, 월별 그래프에서만 하락) |
| `seed_onesided` | 한쪽이 계속 길게 쓰고 질문하고, 상대는 단답 | `strong_me` 또는 `lean_me` |

**`seed_faded`가 중요하다.** 기울기는 `even`인데 월별 그래프는 급락해야 한다. 이게 "기울기 ≠ 관계의 좋고 나쁨"을 증명하는 시드이고, 심화 지표의 존재 이유를 보여준다.

각 시드는 다음을 포함해야 한다.

- 멀티라인 메시지 최소 5개
- 미디어 플레이스홀더 (`사진`, `이모티콘`) 각 10개 이상
- `오전 12:xx` 자정 메시지 최소 3개
- 아침 이어받기 케이스 (전날 밤 종료 → 다음날 오전 첫 메시지) 최소 5개
- 6시간 이상 공백 (세션 경계) 20개 이상
- 삭제된 메시지 2개

## 3. 골든 테스트

### 3.1 파서 골든

시드별로 아래를 JSON에 고정하고 회귀 비교한다.

```json
{
  "seed_onesided": {
    "totalMessages": 412,
    "byWho": { "me": 271, "other": 141 },
    "sessions": 24,
    "bursts": { "me": 63, "other": 62 },
    "media": { "photo": 12, "emoticon": 14, "deleted": 2 },
    "multiline": 7,
    "midnightMessages": 3,
    "unparsedRecords": 0
  }
}
```

**`unparsedRecords: 0`이 가장 중요한 항목이다.** 파서가 조용히 버리는 레코드가 생기면 모든 지표가 틀어진다.

### 3.2 지표 골든

```json
{
  "seed_onesided": {
    "axes": { "msgCount": 0.32, "msgLength": 0.51, "question": 0.44 },
    "tilt": 42,
    "band": "lean_me",
    "axesUsed": 3
  }
}
```

허용 오차 ±1 (반올림 경계). 축이 바뀌면 골든을 갱신하고 **커밋 메시지에 이유를 남긴다.**

### 3.3 상태 계약 테스트

| 입력 | 기대 |
| --- | --- |
| 캡처 시드 | `initiation.status === 'LOCKED'`, `missing: ['continuity']` |
| 캡처 시드 | `emojiAffect.status === 'OK'` |
| txt 시드 | `emojiAffect.status === 'LOCKED'`, `missing: ['affect']` |
| 메시지 20개 캡처 | `phraseGap.status === 'INSUFFICIENT'` |
| 정보 단위 < 25 | 하드 플로어 카드 1장, 리포트 미생성 |

**`LOCKED`와 `INSUFFICIENT`가 서로 바뀌어 나오는 버그를 잡는 테스트다.**

## 4. 경로 일치성 테스트

`PRD.md` §3.3 판독 창의 존재 이유를 수치로 검증한다. **렌더러 채택 시에만 자동화 가능.**

```
시드 txt → 최근 120개 구간 추출 → 렌더러 → 캡처 이미지 N장
                                              ↓
                        txt 경로 기울기  vs  캡처 경로 기울기
```

| 지표 | 목표 |
| --- | --- |
| 밴드 일치율 (시드 3종) | **100%** |
| 기울기 차이 평균 절대값 | **≤ 10** |
| 밴드가 2단계 이상 튀는 비율 | **0%** |

렌더러를 안 쓰면 수동으로 1세트만 만들어 확인한다. **최소 1케이스는 반드시 확인한다** — 심사위원이 교차 검증할 수 있는 유일한 지점이기 때문이다.

> 밴드 일치 목표가 100%인 이유: 시드는 3개뿐이고 의도적으로 서로 다른 밴드로 설계했다. 여기서 어긋나면 실사용에서는 훨씬 심하다.

## 5. 축 상관 측정 (D1)

`SPEC.md` §7.1의 "곱셈 분해로 중복 제거" 주장을 검증한다.

```
시드 3종 × 슬라이딩 윈도우(120개, stride 40) → 창 30개 이상 생성
각 창에서 I_메시지수 / I_길이 / I_질문 계산
축 간 피어슨 상관계수 r 측정
```

| 결과 | 조치 |
| --- | --- |
| 모든 \|r\| ≤ 0.7 | 통과. 결과를 발표 자료에 넣는다 (구조적 방어의 실증) |
| 어떤 \|r\| > 0.7 | 해당 축 교체 후 재측정 |

**변별력도 함께 본다.** 각 축의 창 간 표준편차가 0.05 미만이면 죽은 축이다.

> 특히 `I_길이`를 주시할 것. 한국어 카톡은 짧은 메시지 위주라 평균 길이 차이가 작게 나올 수 있다. 죽은 축이면 `I_동조`를 필수 축으로 승격하는 것이 대안이다.

## 6. 견고성 테스트

| 실패 지점 | 주입 방법 | 기대 동작 |
| --- | --- | --- |
| Vision 스키마 실패 | 잘못된 JSON 반환 목 | 재시도 2회 → 해당 이미지 제외, `gaps` 기록, 나머지로 진행 |
| Vision 2패스 실패 | 에러 반환 목 | C급 지표만 `LOCKED`, 헤드라인 정상 |
| 임베딩 실패 | 타임아웃 목 | 3축 재정규화, "4개 축 중 3개" 표시 |
| LLM 타임아웃 | 12초 지연 목 | 폴백 템플릿, 섹션 1~7 정상 |
| **LLM 수치 조작** | 집계에 없는 숫자를 포함한 응답 목 | **검증 실패 감지 → 폴백 교체** |
| 파싱 부분 실패 | 손상된 레코드 삽입 | 성공 구간만 진행, 정보 단위 재계산 |
| 20MB txt | 시드 반복 확장 | 메인 스레드 블로킹 없음, 진행률 갱신, OOM 없음 |

**LLM 수치 조작 테스트가 §MODELS 5의 존재 증명이다.** 이걸 데모에서 보여줄 수 있으면 "래퍼 아님"의 가장 강한 증거가 된다.

## 8. 데모 리허설 체크리스트

**리허설 2회. 둘 다 처음부터 끝까지.**

- [ ] 바이패스 키가 데모 기기 헤더에 주입되어 있는가 (심사장 단일 IP 대응)
- [ ] 시드 캡처 3종이 로컬에 준비되어 있는가 (즉석 입력 실패 시 즉시 전환)
- [ ] 다크모드 캡처가 사전 테스트를 통과했는가
- [ ] LLM 폴백 강제 토글이 동작하는가
- [ ] 처리 과정 화면의 단계 문구가 실제 진행과 맞는가
- [ ] `LOCKED` 카드가 txt 전환 시 실제로 열리는가 (데모 4번)
- [ ] 이모티콘 정서 카드에 값이 있는가 (데모 2번 — **"복원했습니다" 발언의 근거**)
- [ ] 네트워크 없이 어디까지 되는지 확인 (최악의 경우 대비)

### 데모 실패 시 전환 순서

1. 즉석 캡처 파싱 실패 → 시드 캡처로 즉시 전환, "포맷 방어가 되어 있습니다"로 넘김
2. Vision 장애 → txt 시드로 전환, "두 입력이 있는 이유입니다"로 넘김
3. 전부 장애 → 캐시된 결과 화면으로 전환 (IndexedDB에 시드 결과 미리 적재)

**3번을 위해 데모 전에 시드 3종을 한 번씩 돌려 캐시를 채워둔다.**
